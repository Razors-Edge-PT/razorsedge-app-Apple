## 2. Files to MODIFY

### `lib/WES2_template_service.dart`

**Replace** the Phase-1 stub with a full `FirestoreWes2TemplateService` class implementing the existing abstract `Wes2TemplateService` interface. No changes to the abstract methods.

**`loadTemplate` implementation:**
- Fetches `users/{uid}/templates/{templateId}` from Firestore.
- If doc does not exist â†’ returns `[]`.
- Parses `exercises` list using the same pattern as `Template.fromFirestore`:
  - Expects each entry to be a `Map<String, dynamic>` with `name` (String), `circuitIndex` (int, default 0), and optionally `exerciseId`, `orderIndex`, `setCount`.
  - **Silent skip rule:** if an entry has no `exerciseId` key (legacy templates created without WES2), skip it â€” exerciseId is the mandatory row identity key in WES2.
  - `setCount` defaults to 3 if absent.
  - `orderIndex` defaults to list index if absent.
  - Sets `source = Wes2RowSource.templateLoaded`.
  - Creates `Wes2SetState(setIndex: i)` blank entries up to `setCount` â€” no actual values, no hint values. These are structure-only rows.
- Returns `List<Wes2ExerciseRow>`.

**`saveWorkoutAsTemplate` implementation:**
- Auto-generates a doc ID in `users/{uid}/templates/`.
- Stores: `name` (templateName), `blockId`, `createdAt: FieldValue.serverTimestamp()`.
- `exercises` array: one map per row with `{ exerciseId, name, circuitIndex, orderIndex, setCount }` only. **Never** stores weight, reps, rir, velocity, executionNote, or any actual value.
- Does NOT store `blockAssignment` (requires block metadata lookup, out of scope for Phase 18).

## 6. BB3 CLEARING â€” BLOCKED

**The spec says:** "If replacing BB3 planned exercises, clear entire BB3 planned day."

**Assessment: BLOCKED.**

After reading `WES2_repository.dart` in full: every write method targets only `users/{uid}/workouts/{dateDocId}`. There are **no existing BB3 (planned\_blocks) write paths anywhere in the WES2 codebase**. The structural operations added in Phases 13-14 (deleteExercise, replaceExercise, moveExerciseToCircuit) all write only to the WES2 workout doc.

The BB3 planned day path (likely something under `planned_blocks/{uid}/blocks/{blockId}/...`) is defined in `bb3_*.dart` files. Additionally, `Wes2SessionController` tracks `_activeBlockId` but does **not** track `weekIndex` or `dayIndex`, which are required to address the specific BB3 day sub-document. `WES2_plan_service.dart` reads BB3 to hydrate WES2, but the reverse write direction (WES2 clearing a BB3 planned day) has never been established.

**What IS safe and WILL be implemented:** The WES2 workout document's `wesPlannedExercises[]` will be replaced with template rows (the WES2-owned array). BB3-sourced rows are evicted from the in-memory display. The WES2 workout document will be correct.

**What requires human confirmation before implementation:**
1. The exact Firestore path for the BB3 planned day (the `planned_blocks` sub-document that holds the day's planned exercises).
2. The field name(s) to clear on that document.
3. Whether `weekIndex` and `dayIndex` context is already plumbed through `WES2_plan_service` to the screen, or needs to be threaded through.

Once those are confirmed, a `clearBb3PlannedDay(uid, blockId, weekIndex, dayIndex)` method can be added to `WES2_repository.dart` (which is in the allowed write scope) and called from `_loadTemplate()` after template rows are applied.
