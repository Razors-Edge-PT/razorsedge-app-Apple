GOODLIFT Flutter/Firebase Workout Entry Screen 2
Revision 1 — implementation-ready build contract
Date: 7 May 2026
Status: Source-of-truth specification for autonomous implementation/review
Purpose: This document defines WES2 from product behavior through Firestore contracts, UI rules, state ownership, edge cases, and acceptance tests. It is intended to support an autonomous workflow where Claude Code implements, ChatGPT reviews as specification guardian, and an orchestration script mediates plan -> review -> implement -> test loops.
Non-negotiable principle: BB3 is the planner. WES2 is the execution/logging surface. Planned values are intent and appear as hints. Completed WES2 values are reality.

1. Core Contract and Hard Boundaries
1.1 Non-goals
Do not rewrite progression formulas unless the spec explicitly says so.
Do not migrate the existing planned_blocks hierarchy unless separately approved.
Do not reintroduce hidden BB2 coupling.
Do not treat BB3 planned values as WES2 actual values.
Do not make hint snapshots authoritative server truth.
Do not allow duplicate exerciseIds on the same date via any pathway.
Do not let UI polish override data correctness.
1.2 Locked Implementation Decisions for WES2 v1
These decisions are already settled and must not be re-opened during implementation unless explicitly approved by Richard.
Launch route
WES2 must be added as a separate beta route first. The current WES route must remain untouched until WES2 is proven against the acceptance matrix.
In the UI, this route should be labelled WES2.
For v1, WES2 should be accessible only from the quick access area on the home screen by tapping the WES2 icon. Do not replace the existing Workout Entry Screen route yet.
Completed workout Firestore shape
WES2 v1 must continue using the existing completed workout document:
/users/{uid}/workouts/{yyyy-MM-dd}
Completed workout array fields
Completed exercises must remain in exercises[].
Blank WES2-added or template-loaded planned rows must remain in wesPlannedExercises[].
Do not normalize completed workout data into subcollections in v1.
Because Firestore arrays make direct field-level patching difficult, WES2 must use careful merge or transaction logic on unfocus saves so one device field edit does not wipe another device unrelated field edit.
Isar scope
Isar must be included from the start of WES2 v1.
The first Isar implementation should be narrow and practical, covering:
local day drafts
fast reopen snapshots
offline queued workout saves
expanded/collapsed state
last local edit/scroll position
basic conflict metadata
Do not defer Isar entirely to a later version, because offline save, fast reopen, and resume behavior are core WES2 requirements.
Multi-device live editing
WES2 v1 must include the listener architecture for multi-device editing.
The listener should be field/user-entered-value focused only.
Firestore listener updates should apply after another device saves on unfocus.
Do not live-stream hint recalculations between devices.
Hints are recomputed locally per device from the latest values, BB3 plan, exerciseSettings, and history.
BB3 structural updates from WES2
WES2 v1 must update BB3 planned days for structural changes to BB3-sourced exercises.
This includes:
delete BB3-sourced exercise
replace BB3-sourced exercise
reorder BB3-sourced exercise
move BB3-sourced exercise between circuits
These updates must write back to the BB3 planned day path:
/planned_blocks/{uid}/blocks/{blockId}/weeks/week_{weekIndex}/days/day_{dayIndex}
WES2-only exercises must not update BB3 structure unless/until they become completed according to the BB3 completion rules.
ExerciseSettings dialog
The WES2 exercise settings dialog is part of v1.
It must support in-session edits for:
increments
weekly frequency
rep periodization model
microcycle rep targets
RIR model
current microcycle/session RIR planned targets
progression model
The dialog writes only to:
/planned_blocks/{uid}/blocks/{blockId}.exerciseSettings[exerciseId]
It must not write to plannedExerciseDetails.
ExerciseSettings edits require internet and must not be queued offline.
Current WES reference rule
The current workout_entry_screen.dart may be used as:
behavior reference
visual reference
source for small isolated helper/widget logic where safe
It must not be copied as the WES2 architecture template.
WES2 must remain modular, using the WES2-specific files/services defined in this spec.
v1 feature scope
Timed exercises, velocity, notes, templates, undo, Done state, exercise settings, BB3 handoff, Isar local persistence, and multi-device listener architecture are all part of WES2 v1.
Implementation may be phased internally, but the WES2 beta is not considered handoff-ready until these features are implemented and pass the acceptance matrix.
Duplicate exercise rule
The same exerciseId may not appear more than once on the same date, even across different circuits.
A different exercise variation is allowed only if it has a different exerciseId.
All add/load/template/drag/merge pathways must enforce this silently and defensively.
Blank WES2 planned rows
When a user adds an exercise in WES2 or loads a template row and enters no execution values, the row must still persist immediately in:
wesPlannedExercises[]
This allows blank WES2-added/template-loaded rows to survive page exit/reopen without being treated as completed workout data.
Blank WES2 planned rows do not affect BB3 unless they later become completed according to BB3 completion rules.

3. Firestore and Data Model Contract
3.1 Planned day path
/planned_blocks/{uid}/blocks/{blockId}/weeks/week_{weekIndex}/days/day_{dayIndex}
This path stores BB3 day plans. Example row shape:
{
  circuitIndex: 0,
  exerciseId: "AmfUWbF1DH3I7qPAdh5k",
  name: "Bench Press, Barbell",
  orderIndex: 0,
  sets: [
    { weight: 105, reps: 8, rir: 2 },
    {},
    {}
  ]
}
All values from this location are planned overrides only. In WES2 they appear as hint/plan-note values, never as typed values.
3.2 Block exerciseSettings path
/planned_blocks/{uid}/blocks/{blockId}.exerciseSettings
WES2 uses this block-level exerciseSettings map as the authoritative source for per-exercise model settings. Do not use plannedExerciseDetails for WES2 unless separately approved.
exerciseSettings: {
  exerciseId: {
    defaultSets: 3,
    increments: { primary: 2.5, secondary: 5 },
    periodizationModel: "DUP, By Exposure",
    progressionModel: "Smart Progression",
    repTargets: { week1: { instance1: "5 x 3", instance2: "3 x 3" } },
    rirModel: "Static RIR",
    rirPlan: { week1: { session1: { set1: { reps: "5", rir: "2.0" } } } },
    weeklyFrequency: 2,
    modelSpecificRepTargets: { "Linear, Classic": [15, 20, 16, 18] }
  }
}
3.3 Completed workout path
/users/{uid}/workouts/{yyyy-MM-dd}
Existing structure includes completed exercises and WES-only planned rows:
{
  date: "2026-04-27T00:00:00.000Z",
  name: "Monday 27 April 2026",
  userId: "{uid}",
  lastEditedAt: Timestamp,
  exercises: [
    {
      circuitIndex: 0,
      orderIndex: 0,
      exerciseId: "AmfUWbF1DH3I7qPAdh5k",
      name: "Bench Press, Barbell",
      setCount: 2,
      isMarkedDone: true,
      sets: [
        { weight: 120, reps: 4, rir: 2 },
        { weight: 117.5, reps: 3, rir: 2.5 }
      ]
    }
  ],
  wesPlannedExercises: [
    {
      circuitIndex: 0,
      orderIndex: 1,
      exerciseId: "ocNWJv7xLrlinGmjG6cV",
      name: "Machine Row, Supported",
      setCount: 3,
      sets: [],
      createdAt: Timestamp
    }
  ]
}
3.4 Exercise row shape
Use the same structural shape for rows in both exercises[] and wesPlannedExercises[]:
{
  exerciseId: String,
  name: String,
  circuitIndex: int,
  orderIndex: int,     // global day order, not local within circuit
  setCount: int,
  sets: List<Map<String, dynamic>>
}
Rows in exercises[] may additionally include:
{
  isMarkedDone: bool
}
setCount lives on both exercises[] and wesPlannedExercises[].
orderIndex lives on both exercises[] and wesPlannedExercises[].
isMarkedDone lives only on exercises[].
sets[] stores actual entered fields only. Do not store model hints as actual values.
Blank added sets persist via setCount even if sets[] has no value at that index.

4. State Ownership and Identity Rules
4.1 Exercise uniqueness
An exercise may appear only once per date across all circuits.
All add/load/template/drag/merge paths must silently guard against duplicates by exerciseId.
If duplicate data is encountered from legacy/cache/server, WES2 should keep the first valid row in global order and discard/merge duplicates conservatively.
4.2 Identity
exercise identity = date + exerciseId
set identity      = date + exerciseId + setIndex
field identity    = date + exerciseId + setIndex + fieldKey
Do not use row index as durable identity. Row order changes through drag/drop, circuit moves, and template replacement.
4.3 Source flags
Every in-memory WES2 row should track source metadata to decide sync behavior:
enum Wes2RowSource {
  bb3Planned,
  wes2Manual,
  templateLoaded,
  completedServer,
  localDraft
}
BB3-sourced structural edits update BB3 planned day where applicable.
WES2-only rows do not update BB3 until completed according to BB3 completion rules.
Completed rows are always saved as WES2 reality under /users/{uid}/workouts/{date}.

5. Opening, Loading, Fast Paint, Refresh, and Save Lifecycle
5.1 Initial route behavior
Open from homepage: selected date defaults to today.
Open from calendar picker: selected date equals chosen date; past and future dates allowed.
Swipe left/right on date/header area: navigate previous/next day.
On date change, begin a new date session and prevent stale loaders from writing into the new page.
5.2 Loading order
Local Isar draft/snapshot for instant paint.
Server completed workout day / WES2 planned rows.
BB3 planned day.
Block exerciseSettings.
Top-set/history/bodyweight data required for hints.
Initial hint recomputation.
No full-page spinner.
During load show "Wait for it..." where exercises will appear. Ellipsis animates like original WES.
If empty after load: "No exercises planned yet, add some to get started".
Partially completed workout reopen should feel instant and editable immediately.
5.3 Add during load
Add Exercise picker can open immediately even while day is loading.
If user selects exercises before day is fully resolved, queue insertion.
Show: "Adding those exercises, sit tight...".
Apply queued adds only after existing day rows, BB3 rows, settings, and initial hints are resolved.
5.4 Save triggers
Save on field unfocus.
Save on page exit.
Save on app background.
Save on app shutdown/best-effort lifecycle event.
Save current corrected state after undo on next save trigger; background save after undo is allowed but must not block UI.
Saving should be Google Sheets-like: edits become durable on unfocus, not only on a final Save button.

6. Planned vs Completed Exercises and BB3 Handoff
6.1 Completion concepts
If an exercise is added in WES2 and left blank, it stays in WES2 for that date but does not affect BB3. If it becomes completed, BB3 shows it as completed.
6.2 BB3 planned values in WES2
BB3 planned values override corresponding model hints, but only as hint values.
If user clears a WES2 typed field, the relevant BB3 planned hint or model hint reappears.
Existing typed values never get overwritten by changes in BB3 or exerciseSettings refresh.
BB3 plan notes show as planned note indicators, distinct from WES2 execution notes.

7. Hint, Periodization, Progression, and History Contract
7.1 Hint priority
WES2 typed/completed value.
Current local draft value.
BB3 explicit planned override hint.
Model/progression hint.
Empty.
7.2 Instant recalculation
Weight entry immediately updates rep hints where relevant.
Rep entry immediately updates weight hints where relevant.
RIR/RPE entry immediately updates weight/reps hints where relevant.
If RIR changes as a consequence of locked weight/reps, show subtle visual cue/background shift because RIR deviation is important.
Set 2+ hints update when Set 1 or prior sets change.
No save debounce is required; field unfocus saves. Hint recalculation can be synchronous/local and must not lag.
Typed field text must never be rewritten during hint recomputation. Caret/cursor must not jump.
7.3 Periodization target use
DUP By Week uses weekly/microcycle instance index.
DUP By Exposure uses global exposure index cycling through microcycle targets.
Linear models interpolate between provided variables across the block.
DUP Signature rep target is a min-max range, e.g. "3 - 15"; set count defaults to 3.
For repTargets like "5 x 3", reps = 5 and set count = 3. In DUP week/exposure, week1 is the microcycle pattern, not literal block week only.
7.4 Progression target use
Progression model overlays periodized rep target and RIR to determine suggested weight/reps/RIR combination.
Top-set history anchors target E1RM and progression decisions.
Smart Progression nudges E1RM by the smallest reasonable amount using increments and rep range constraints.
Linear Weight Increase adds smallest available increment once target criteria are met.
Add Reps model adds reps until threshold conditions allow weight increase.
Progression anti-repeat logic must not override explicit planned rep targets. If the plan says 6 and 8, the plan remains 6 and 8 even if a user previously performed 7.
7.5 E1RM display
If only hints exist, E1RM displays in hint/grey style as projected E1RM.
Once weight and reps are entered, E1RM switches to completed/actual style.
RIR participates in E1RM math when available; if absent, use existing model behavior/fallback consistently with current WES.
7.6 Best reps at / best weight at labels
Read-only labels. Tapping does nothing.
Best reps at = best reps ever achieved at current Set 1 hint/completed weight, if history exists.
Best weight at = best weight ever achieved at current Set 1 hint/completed reps, if history exists.
Use all historical completed sets for the user/exercise where the relevant comparison value exists. Prefer exact matches; if the current WES logic has a tolerance, preserve that tolerance.
Do not require RIR for these labels unless current WES logic does so.
Tie-breaker: newest value wins if same best result; otherwise highest reps/weight wins.

12. Multi-device, Offline, Local Persistence, and Conflict Policy
12.1 Local persistence technology
Use Isar for local persistence/snapshots. Do not choose Hive for WES2 unless separately approved.
Isar should store day-scoped local drafts, hint snapshots for fast paint, expanded/collapsed state, last local edit position, queued offline workout saves, and last known server metadata required for conflict detection.
Cache keys must include uid/actingAsUid and date. Never cross-contaminate coach/athlete users.
Local hints are speed/resume hints only, not durable truth.
12.2 Online simultaneous editing
WES2 should behave like Google Sheets for simultaneous editing.
Use Firestore listener(s) on the workout document/day for live user-entered value updates.
Updates are broadcast to other devices on field unfocus/save only.
Two users can edit different fields at the same time; both survive.
If two users edit same field, last unfocus/write wins.
If Device A edits set 1 weight and Device B edits set 1 reps, both updates coexist.
If Device A edits set 1 and Device B edits set 2, both updates coexist.
Live sync applies only to user-entered values and workflow flags. Do not live-stream hint recalculations between devices.
Refresh button still reloads latest user-entered values and latest BB3 hints/settings.
12.3 Collaborator editing indicator
When another active user/device is editing a field, show subtle colored border around that field.
Border only; no heavy collaborator UI required.
This indicator is advisory. Last unfocus/write still wins.
Presence/field-focus metadata may be stored in lightweight Firestore presence document or subfield with TTL/lastSeenAt, but must not introduce typing lag.
12.4 Save granularity
To support Google Sheets-like collaboration without lag, saves should be granular enough that one field update does not wipe unrelated fields from another device.
WES2 v1 keeps the existing exercises[] and wesPlannedExercises[] array structure. Do not normalize completed workout data into subcollections in v1.
Because arrays cannot be safely patched at arbitrary nested indexes without conflict risk, unfocus saves must use a safe transaction/merge strategy: read the latest server row, apply the local field patch by exerciseId + setIndex + fieldKey, preserve unrelated newer fields, then write back the corrected array.
Avoid full-document overwrite on every field unfocus unless a merge layer guarantees unrelated fields survive.
Structural changes such as reorder/template replace may write whole day state atomically, but should first account for current latest server state and local dirty state.
12.5 Offline queued saves and rare conflict prompt
If offline, save WES2 workout changes locally and queue sync.
If the same workout was edited online on another device after this local offline edit, conflict resolution is whole-workout choice, not per-field manual merge.
Prompt language should be user-friendly, e.g. "This workout was changed on another device while this device was offline. Which version do you want to keep?"
Choices: Keep this device’s workout / Use latest online workout.
This prompt appears only for unsynced offline conflict scenario.
Normal online simultaneous edits do not prompt; they follow field/set-level last-write-wins.
12.6 Last write wins
Online normal field conflict: last field unfocus/write wins for that exact field.
Set-level/exercise-level unrelated fields should merge, not wipe each other.
Structural conflict: most recent structural save wins for the affected day/structure unless offline conflict prompt applies.
Local scroll position and expanded/collapsed states are per-device only and never synced.

13. Retroactive Edits and Future Hint Recalculation
If a historical workout is edited retroactively, future hint calculations should behave as if the edited values were the original values entered at that time.
This affects top-set history, E1RM baselines, progression decisions, and exercise instance counts from that date forward.
User-entered values in later completed workouts are never overwritten.
Hints underneath existing user-entered values may change after refresh/recalculation.
Uncompleted future/planned fields may show new hints if the retroactive edit changes the relevant history/instance/progression context.
BB3 planned explicit overrides should not be overwritten by retroactive hint recalculation unless the user separately edits BB3/planning data.
Refresh/recompute should be enough to show corrected hints after retroactive edits.

14. Implementation Architecture / Suggested Modules
Build WES2 as new modular architecture, not as a copy/paste monolith of current WES.
14.1 Field state model
class Wes2FieldState<T> {
  T? actualValue;      // typed/completed value
  T? hintValue;        // BB3 planned override or model hint
  FieldOrigin origin;  // empty, typed, completed, bb3Hint, modelHint, localDraft
  bool dirty;
  DateTime? lastEditedAt;
}
This model is essential for keeping typed values, hints, and visual states separate.
14.2 Save safety
Use epoch guards on date changes to prevent stale async loaders from writing into wrong date.
Every Firestore write must use UserContext.currentUid/actingAsUid.
Local cache keys must include uid + date.
Every structural operation should normalize circuitIndex/orderIndex before saving.
Do not block typing on Firestore.

17. Final Hard Rules
Never overwrite a user-entered WES2 value with a hint.
Never treat BB3 planned values as completed WES2 values.
Never key durable data by row index.
Never allow duplicate exerciseId on the same day.
Never silently discard local unsynced workout progress.
Never queue exerciseSettings edits offline.
Never let a save path use FirebaseAuth.currentUser.uid when UserContext.currentUid is required.
Never let live hint recalculation introduce typing lag.
Never let structural Firestore writes leave circuitIndex/orderIndex in inconsistent state.
Never remove current WES until WES2 passes acceptance matrix.
