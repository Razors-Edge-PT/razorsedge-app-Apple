### 4. Firestore Read/Write and Merge/Transaction Strategy

**Read paths**
- `/users/{uid}/workouts/{yyyy-MM-dd}` â†’ completed `exercises[]` + `wesPlannedExercises[]`
- `/planned_blocks/{uid}/blocks/{blockId}/weeks/week_{n}/days/day_{n}` â†’ BB3 planned day
- `/planned_blocks/{uid}/blocks/{blockId}` â†’ `.exerciseSettings` map

**Write paths and safety**

*Field unfocus save (granular)*: Because Firestore arrays cannot be field-patched safely, `WES2_repository.dart` uses a **Firestore transaction** on unfocus:
1. Read latest server document snapshot within the transaction.
2. Locate the target exercise row by `exerciseId` (not index).
3. Apply only the changed `fieldKey` at `setIndex` â€” preserve all other fields from the server snapshot.
4. Rewrite the corrected array and commit.

This prevents Device B's reps from being wiped by Device A's concurrent weight write (Â§12.4).

*Structural saves (reorder, template load, replace)*: Write full normalized day state atomically in a single `set()` with `merge: false` on the workout document, but only after reading and reconciling the latest server state + local dirty state. Gate behind epoch guard to prevent stale async loaders from committing.

*BB3 structural writeback*: `WES2_plan_service.dart` writes `/planned_blocks/{uid}/blocks/{blockId}/weeks/week_{n}/days/day_{n}` for delete/replace/reorder of BB3-sourced exercises only. These use `update()` on specific fields within the day document, not full overwrites.

*ExerciseSettings*: `update({'exerciseSettings.${exerciseId}': newSettings})` on the block document. Requires internet; never queued.

**Epoch guard**: `WES2_session_controller.dart` increments a `_epoch` counter on every date change. Every async loader captures the epoch at start and checks it before committing results â€” stale loaders for previous dates silently discard their results.

### 5. Isar / Local Draft / Fast-Reopen / Offline Queue Strategy

`WES2_local_store.dart` owns all Isar interactions. New Isar collections (modelled after `ClaudeBulletSnapshot`):

| Collection | Key | Content |
|---|---|---|
| `Wes2DayDraft` | `uid + date` | Full serialized day state as JSON: rows, setStates, `Wes2FieldState` payloads, `dirty: bool`, `lastLocalEditAt` |
| `Wes2ExpandedState` | `uid + date + exerciseId` | `expanded: bool` (device-local, never synced) |
| `Wes2ScrollPosition` | `uid + date` | Last scroll offset + `lastEditedExerciseId` + `lastEditedSetIndex` |
| `Wes2OfflineQueue` | `uid + date + queuedAt` | Serialized save payload + retry metadata |
| `Wes2ConflictMeta` | `uid + date` | Last known server `lastEditedAt` timestamp; used for offline conflict detection |

**Fast reopen**: On page open, `WES2_local_store.dart` returns the `Wes2DayDraft` instantly â†’ `WES2_session_controller.dart` paints with it. Server load runs concurrently. If server data is newer than draft, merge server data preserving locally-dirty fields (by comparing `lastLocalEditAt` vs server `lastEditedAt`).

**Offline queue**: If no internet on unfocus, save to `Wes2OfflineQueue`. On reconnect, process queue in order. Before committing each queued item, compare `Wes2ConflictMeta.lastKnownServerTimestamp` with current server `lastEditedAt` â€” if server is newer (edited online while offline), show whole-workout conflict prompt.

**Coach/athlete isolation**: Every Isar key includes `uid` = `UserContext.currentUid` (i.e. `actingAsUid`). Switching athlete clears/ignores prior athlete's local store keys.

### 6. Multi-Device Listener Strategy

`WES2_sync_service.dart` opens a `StreamSubscription` on `/users/{uid}/workouts/{date}` when WES2 page is active.

**Listener apply rules**:
- On each snapshot: extract `exercises[]` and `wesPlannedExercises[]` from server.
- For each exercise row (matched by `exerciseId`), for each set, for each field: if the local `Wes2FieldState.dirty == false` for that field, accept the server value. If `dirty == true` (user is editing or has unfocused since load), keep local value.
- Never apply hint recalculations from server â€” hints are always recomputed locally.
- Structural changes (row added/deleted/reordered on another device) are applied only if local state for that row is clean.

**Collaborator field border**: A lightweight Firestore presence document at `/users/{uid}/workouts/{date}/_presence/{deviceId}` stores `{focusedExerciseId, focusedSetIndex, focusedField, lastSeenAt}` with a TTL. `WES2_sync_service.dart` listens to `_presence` sub-documents. If another device's `lastSeenAt` is within 30s, the matching `WES2_field_tile.dart` shows a 1px colored border. This never blocks typing.

**No inter-device hint streaming**: Hints are pure local computations. The listener only carries `actualValue` fields.

### 7. BB3 Structural Sync/Update Strategy

`WES2_plan_service.dart` handles all BB3 writeback. Rules:

| WES2 action | BB3 row source | BB3 writeback |
|---|---|---|
| Delete exercise | `bb3Planned` | Remove that exercise from BB3 planned day array |
| Delete exercise | `wes2Manual` / `templateLoaded` | No BB3 writeback |
| Replace exercise | `bb3Planned` | Replace in BB3 planned day with new exerciseId |
| Reorder within circuit | `bb3Planned` | Update `orderIndex` in BB3 planned day |
| Move between circuits | `bb3Planned` | Update `circuitIndex` + `orderIndex` in BB3 planned day |
| Load template (any source) | replaces day | Clear entire BB3 planned day; template rows become `templateLoaded` |
| WES2-only exercise completes | `wes2Manual` | No BB3 writeback (BB3 reads completed workout doc directly) |

All BB3 writes use `update()` on the day document, patching only the `exercises` array (or specific fields) after normalizing `circuitIndex` and `orderIndex` across all affected rows.

Undo queues the inverse BB3 writeback but does not immediately fire it â€” the next save trigger applies the corrected state.

### 8. Hint/Progression Integration Strategy

`WES2_hint_service.dart` is a thin orchestration wrapper around the existing read-only `periodization_model_utils.dart` (PMU) and `progression_engine.dart`. It is **never** modified; WES2 calls it with synthetic inputs matching the pattern established in `bb3_hint_service.dart`.

**Hint priority chain** (per `Wes2FieldState.hintValue`):
1. `actualValue` present â†’ show actual, no hint display needed.
2. BB3 explicit planned override (field non-null in `BB3Set`) â†’ hint from BB3.
3. PMU/ProgressionEngine model hint â†’ derived from `exerciseSettings`, top-set history, block week/instance context.
4. Empty.

**Computation trigger**: Every field `onChanged` in `WES2_field_tile.dart` calls `WES2_session_controller.recomputeHints(exerciseId)` synchronously (no debounce, no Firestore). The controller updates sibling `Wes2FieldState.hintValue` values and calls `setState` only on the affected exercise card â€” not the full page. Typed field text is never touched during recomputation.

**Set 2+ hints**: Derived from Set 1 target/actual + fatigue/dropoff factor + RIR plan â€” replicating the existing WES set-cascade logic read from `workout_entry_screen.dart` as behavior reference.

**Instance index computation**: Resolved by `WES2_plan_service.dart` at load time â€” DUP By Week uses `weeklyInstanceIndex` (position within current week, keyed by `weeklyFrequency`); DUP By Exposure uses global completed exposure count from history.

### 11. Risks and How the Plan Avoids Touching Blocked Files

| Risk | Mitigation |
|---|---|
| **`workout_entry_screen.dart` accidental edit** | WES2 is a fully separate file tree. The only cross-reference is read-only behavioral inspection. No import of WES2 into WES1 or vice versa. |
| **`main.dart` route wiring** | Spec and hard restrictions both prohibit v1 main.dart edits. WES2 is reached only via the `home_screen.dart` Quick Access `MaterialPageRoute` â€” no named route registration needed. |
| **`periodization_model_utils.dart` / `progression_engine.dart` modification** | `WES2_hint_service.dart` calls these as read-only dependencies using the same synthetic-input pattern as `bb3_hint_service.dart`. No edits to either file. |
| **`pubspec.yaml` / assets** | Isar is already a dependency (existing `isar_claude_bullet_snapshot.dart` proves it). No new packages or assets needed in v1. |
| **BB3 files (`bb3_*.dart`)** | `WES2_plan_service.dart` reads BB3 planned day and writes to BB3 planned day paths via Firestore SDK directly â€” no imports of or edits to the BB3 dart files. |
| **Firestore schema breaking change** | WES2 v1 is additive only: `setCount` and `orderIndex` fields added to existing array rows; `wesPlannedExercises[]` already exists. No subcollection normalization, no schema migration. |
| **Isar model collision** | WES2 Isar collections (`Wes2DayDraft`, etc.) are new classes in `WES2_local_store.dart`. They do not modify `ClaudeBulletSnapshot` or any existing `isar_*.dart` model. |
| **Coach/athlete UID leakage** | Every Firestore path and Isar cache key uses `UserContext.currentUid` (`actingAsUid`). `FirebaseAuth.currentUser.uid` is never used directly in WES2. This is enforced at the `WES2_repository.dart` layer. |
| **Circular calendar-picker regression** | Calendar-picker navigation in `home_screen.dart` at line ~3025 is never touched; it continues to open `WorkoutPage`. WES2 Quick Access card is a separate widget inserted nearby. |
| **Stale async loaders overwriting correct date** | Epoch guard in `WES2_session_controller.dart` invalidates all in-flight loaders on date change. |
| **`bb3_*.dart` files accidentally edited** | `WES2_plan_service.dart` owns all BB3 path logic and is the only file that writes to BB3 Firestore paths â€” no other WES2 file touches BB3 paths directly. |
